## Phase 27: New kart items
- **My original item is the Magnet:** for 6 seconds you pick up coins from 10 m away instead of 2 m, and you get a slipstream (up to +4 m/s) toward the kart just ahead when it's within 30 m. Chosen because coins already raise top speed in our game, so the Magnet feeds an existing system instead of adding a new one, and it rewards chasing rather than attacking.
- **Lightning Bolt:** shrinks every kart *ahead* of the user for 3.5 s (top speed ×0.72, much lighter in bumps, speed ×0.6 at the strike), with no spin-out, so it's strong but not cruel. A Shield blocks it and is used up. Karts that already finished aren't touched. Only karts near the back can get it (15 % at the back, never at the front).
- **Triple Slick:** stays in your item box with a "×3" counter; each ITEM press drops one slick. The computer drops its three about 0.7 s apart.
- **Odds** were rebalanced so the new items appear without crowding out the old ones (see `ITEM_ODDS` in karts-data.js).

## Phase 28: Glide-ramp track (Cloud Gardens)
- **Theme:** gardens above the clouds (pink-and-blue sky, puffy clouds, floating rock islands with lawns, trees). Original look, built from code plus the trees we already ship.
- **What a "shortcut" is:** the road stays one closed loop (so lap counting, race places and the barriers keep working). A shortcut ramp is a narrow ramp on *one side* of the road, on the side facing the landing. Taking it is a choice: line up on that side or drive past. The flight goes straight across the gap and lands further along the same lap, skipping a long loop of road (~110 m of flight saves ~120 m of road, about 4 s).
- **Flight rules:** during a shortcut flight the kart's lap position follows how far across the gap it is, so race places update smoothly and the finish line can't be skipped. An invisible arc (6 m high in the middle) keeps the glider from sinking into the gap, and it keeps at least 20 m/s, so a hit in mid-air can't leave anyone stuck. Glowing orange hoops show the line, and the minimap draws dashed lines.
- **Ramps on this track:** three in total: one full-width glide down from the hilltop (blue posts) and two shortcut ramps (orange hoops on their posts).
- **Computer racers** take a shortcut about 45 % of the time (decided once per ramp per lap), so they stay beatable but you'll see them use it.

## Phase 30: Kart pad didn't appear on a real phone
- **What I found:** I could not make it fail here: in a headless browser, one phone and two phones both switch to the kart pad. The old design had one weak spot, though: the console told the phones "show the kart pad" exactly **once**, when the race started. A phone that missed that one message (a Wi-Fi hiccup, the phone briefly pausing the page, a reconnect at the wrong moment) stayed on the normal remote for the whole race. And with rotation lock on, an upright phone only showed "Turn your phone sideways".
- **Fix (so it can't get stuck any more):** the server now remembers which layout the room uses and gives it to every phone that joins or comes back; the console repeats it every 2 s during a race; the pad works with rotation lock on (it turns itself sideways). The `?debug=1` readout on the phone now says where the layout came from and what is really on screen, so if it still happens we'll see why.
- **Protocol:** this adds one field (`layout`) to the join answer and changes no event names. CLAUDE.md says to ask before protocol changes; you asked for a fix without stopping, so I kept it to this backward-compatible addition.
- **The motion-sensor note** ("Motion is allowed, but the sensors send nothing…") no longer appears over the kart pad, because it covered GAS and BRAKE.
- **Steering buttons:** holding LEFT/RIGHT builds up to a full turn in 0.16 s instead of jumping, so a quick tap is a small correction (digital full lock felt twitchy in the tests); letting go straightens in 0.08 s. If both are held, the newest press wins.
- **Browser test:** it needs Playwright, which isn't one of this project's dependencies, so I did not add it to package.json; the test skips itself when Playwright is missing.

## Phase 33: Phone zoom bug
- **Cause:** the phone page's viewport tag forbids zooming, but iPhone Safari ignores that tag, so a double tap zoomed the page in and it stayed zoomed (the LEFT button then sat off screen).
- **Fix:** `remote/no-zoom.js` stops pinch gestures, swallows a second tap within 0.4 s (except in text boxes), and, if the page is somehow zoomed anyway, snaps it back by re-applying the viewport. The page height also uses the visible height (`100dvh`), so a browser toolbar can't push the bottom buttons off screen.
- **Cursor ("working poorly"):** the phone-side pointer code is unchanged since Phase 21 (the version that felt much better), so I did not change anything for it without a symptom. Asked the user for one (laggy / jumpy / drifting / wrong speed / only in a certain screen) plus the `?debug=1` numbers.

## Phase 34: First real-phone test
- **Cursor going in different directions:** I compared our pipeline with OpenWii's line by line. The pointer code (`gyro-pointer.js`, `orientation.js`) is byte-identical to OpenWii's, and the phone sends the same sensor fields. I could not find a regression, so instead of guessing I added a **Steady cursor** switch: it ignores the learned gyro axis map (the one part that can lock onto a wrong mapping on some phones) and uses the fused orientation only. If Steady fixes it, the cause is the gyro mapping on that phone. If it doesn't, the next test is running OpenWii itself on the same phone (see the final message): if its cursor misbehaves too, it's the phone/browser sensors, not our code.
- **Karts hopping:** a real bug in the rules. After a landing the vertical speed was reset to 0, but on a downhill the road keeps falling away, so the kart took off again the next step and hopped all the way down (desert: 106 hops in 80 s, now ~6, Cloud Gardens 52 → 2). Landing now keeps the road's vertical speed, and a crest only launches you when the road curves away faster than gravity (`CREST_G = 0.9`).
- **Karts "stopping":** every wall touch cost 40% of the speed. A graze along the barrier now barely slows you; only a head-on hit costs speed (up to 40%, scaled by the angle).
- **Alien Strike:** you ran from bullets because nothing said you could shoot. Now a how-to-play screen explains the goal first, and holding A keeps firing.
- **"Copy the original games" (Mario Kart, Fruit Ninja):** I did not recreate Nintendo's or Halfbrick's characters, courses, music or art, even for private use. Their game *mechanics* (item boxes, drifting with mini-turbos, gliders, slicing fruit with combos) are already in our games. For the polished originals' feel, OpenWii (MIT code) can be run next to our console as a separate app.

## Phase 35: Cursor after the kart pad (user's suspicion)
- **Diff since Phase 21:** the phone's motion code (`motion.js`) and the whole pointer pipeline (`gyro-pointer.js`, `orientation.js`, engine) are unchanged apart from the options I added (Steady cursor). What changed is the layout code around them: the wheel pad became the kart pad, the page can now rotate, and the console re-sends the layout every 2 s.
- **The hypothesis:** the kart pad turns the phone to landscape; does the learned gyro axis map stay wrong afterwards? In simulation (spec, radians, mirrored and swapped gyro conventions) a portrait → landscape → portrait round trip does **not** corrupt the map, so I can't prove that is what happened on the real phone. But I tested the failure itself: if a phone's reported axes change mid-session, a stale map leaves the cursor clearly off (error 0.177) and only `relearn()` fixes it (0.055).
- **Fix:** `Pointer.relearn()` forgets the map and trust (the cursor follows the fused orientation, which is always right, until the gyro earns trust again after about a second of motion). The console calls it on every layout switch (menu <-> kart pad <-> keyboard), and the phone asks for it when its screen orientation changes (`input:recenter` with `{ relearn: true }`, a backward-compatible addition to the protocol, noted in protocol.js).
- Steady cursor stays as the backup option (Settings, or G).

## Phase 44: Photos hub
- **Server** (`server/photos.js`): uploads are `multipart` (`photo` + optional `thumb`), 15 MB each, saved under random ids in `data/events/<id>/photos|thumbs`, listed in `photos.json`. The bytes decide the type (JPEG, PNG, WebP, GIF, HEIC); a web page renamed `.jpg` gets 415. SHA-256 on the server skips duplicates. Limits: 40 uploads per phone per minute (429), the event's photo limit (507 `LIMIT`), and less than 300 MB free on the laptop (507 `DISK_FULL`). Photos are served by their unguessable id (80 bits, only listed to people in the room); hidden or waiting photos are 404 for everyone but the host. Hide/approve are host-only; delete is the owner or the host. Everything is announced live (`party:photo`) to the TV and the phones that may see it.
- **Phone** (`remote/photos.js`): each photo is decoded (`createImageBitmap`, falling back to an `<img>`), drawn on a canvas at most 3000 px, and re-encoded as JPEG 0.88, which also **removes GPS/EXIF**; a 480 px thumbnail goes up with it. If the phone cannot decode it (HEIC on Chrome) the original goes up unchanged and the album shows "No preview". Two uploads at a time with real progress bars (XHR), Retry per photo, a "keep this page open" note, and a leave-page warning while uploads run. Gallery: All/Mine, live updates, full-screen viewer with swipe and pinch zoom, **Save** through the share sheet (so an iPhone offers "Save Image") with a plain-download fallback, **Select -> Save selected** in batches of 10, **Download all (ZIP)** with a size warning, and delete for your own photos.
- **TV** (`channels/photos.js`): wall (calm slideshow, a new photo jumps the queue with a chime and shows for 6 s), grid (PLUS), full screen (A), hide with MINUS (asks first), and a waiting list when "approve first" is on. An empty album shows the QR. Pictures from the laptop's `photos/` folder still appear (marked "Laptop"). A toast tells you about new photos while you are elsewhere.
- **Not done / differences from the plan:** the uploader's EXIF stripping relies on canvas re-encoding (so animated GIFs lose their animation); "Open album folder" is replaced by the ZIP download (a browser page cannot open a folder); pinch-zoom is written by hand because the page-wide zoom guard blocks the browser's own. Upload speed was not measured on real Wi-Fi with 20 photos from 3 phones: the automated test sends 3-12 photos from 2 phones through the real server and browsers.
- Tests: `party-photos` (6, server), `party-photos.e2e` (real browsers: upload, live on two phones, viewer, save as download, delete, TV wall jump). Screenshots: `docs/screenshots/p44_*.jpg`.

## Phase 45: Music hub
- **Rules** (`server/music.js`, all plain functions, 7 unit tests + an HTTP test with a pretend YouTube): fair order = a person's 1st waiting song, then everyone's, then their 2nd...; inside a round more votes first, then whoever added first. 3 songs waiting per person, no duplicates, one vote per person per song (not for your own song; a second tap takes it back), skip when votes reach max(2, 40% of the people online), the host can skip, remove and move songs (a hand-made order comes first), only the adder or the host can remove. The TV reports `music:ended` / `music:error`; the server advances (an old notice is ignored) and names the person whose song failed.
- **Adding:** links in every common YouTube form are parsed (watch, youtu.be, shorts, embed, live, music.youtube.com, bare id). ## Phase 46: Present hub
- **Server** (`server/present.js`): decks live in `data/events/<id>/decks/<deckId>/` (a `file.pdf`, or `1.jpg 2.jpg...` plus small `t1.jpg...`). Uploads are checked by their bytes (a PDF starts with `%PDF-`; pictures must be JPEG/PNG/WebP/GIF), PDFs up to 60 MB, pictures 15 MB each, 80 slides. A `.pptx/.ppt/.key/.odp` is refused with the export steps (HTTP 415, the phone shows them in a box). Files are served by the deck's unguessable id. One presenter at a time (409 `BUSY` for others), only the presenter or the host turns pages / blanks the screen / uses the laser / ends the show, the host can take over, the deck remembers the last page, notes belong to the deck's owner, and deleting the deck on stage ends the show.
- **TV** (`slides.js`): a full-screen layer on top of the menu and the Photos/Music screens but hidden while a game is open. PDFs are drawn by **pdf.js** (the *legacy* build: the newest one needs JavaScript features that the test browser and older Safari lack; its fonts and character maps are served from `node_modules` at `/vendor/pdfjs-dist`). The next and previous slides are drawn ahead; a page turn is a 150 ms crossfade (and none with reduced motion). The TV also counts the pages of a new PDF and makes small page pictures in the background (the phones need them for "now / next"). Keyboard and USB clickers: arrows, PageUp/Down, Space, Enter, Backspace; **B** or **.** = black, **Esc** = end; the remote's A/RIGHT = next, LEFT = back, B = black, HOME = end the show.
- **Phone** (`remote/present.js`): library with upload (PDF, or pictures with name, reorder and remove before uploading; pictures are shrunk to 2000 px with a thumbnail), the presenter view (Prev/Next on `pointerdown` so two quick taps both count, swipe, now/next pictures, a timer that starts with the show and resets on tap, notes, End), and a note for everyone else saying who presents and where they are.
- **Laser:** the presenter holds a button; the phone streams its motion (`present:motion`) and the same gyro engine as the cursors (with a virtual "laser" id) turns it into the red dot. Guests get it too: motion permission is asked only at their first press, never at joining. Works only over https (motion sensors need it): the phone says so.
- **Not tested here:** the laser on a real phone (the sandbox has no sensors; the relay rules are tested, the dot is not), presenting a 20-page real-world PDF with embedded fonts (a generated 4-page PDF was used), and the phone's Present tab on iOS Safari. The TV auto-shows the slides but does not zoom out of a tile like games do.
- Tests: `party-present` (4, server), `party-present.e2e` (real browsers: PowerPoint help, upload, the TV draws page 1 red then page 2 blue by checking canvas pixels, page turns from the phone and the TV keyboard, black screen, ending). Screenshots `docs/screenshots/p46_*.jpg`.
